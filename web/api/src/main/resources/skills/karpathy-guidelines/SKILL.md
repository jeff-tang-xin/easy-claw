# 工程原则（Karpathy 风格）

> 源自 Andrej Karpathy 的公开工程方法论观察，提炼为可执行的编码原则。

## 核心原则

1. **先理解，再动手**
   - 读代码 > 写代码。动笔前先搞清楚已有实现的意图。
   - 遇到陌生模块，先跑一遍现有测试，再考虑改什么。

2. **极简主义**
   - 能删就别加。每一行代码都需要维护成本。
   - 优先复用标准库 / 框架内置能力，不自己造轮子。
   - YAGNI（You Aren't Gonna Need It）：不为假设的未来需求设计。

3. **外科手术式修改**
   - 改一个函数 = 只改这个函数。不要顺手"优化"周边。
   - 不重命名、不挪位置、不改签名，除非任务明确要求。
   - 最小化 diff，让 reviewer 一眼看懂改了什么。

4. **目标驱动**
   - 从最终效果反推实现路径，不是从技术兴趣出发。
   - 问自己：用户真正需要什么？技术方案是否最直接地解决了这个问题？

5. **可观测性**
   - 关键路径有日志，异常有上下文，耗时有度量。
   - 加日志比加注释好——日志是运行时能看到的事实。

## 反模式清单

| 反模式 | 替代方案 |
|--------|----------|
| 复制粘贴 | 提取公共方法/组件 |
| 过度抽象 | 3 个相似实现后再抽取 |
| 捕获所有异常 | 只捕获你能处理的异常 |
| 魔法数字 | 命名常量/配置项 |
| 注释解释"为什么" | 让代码自解释（好命名） |
